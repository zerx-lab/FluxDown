## 日志系统

**引擎滚动日志**：格式 `HH:MM:SS.mmm [Tag] message`；这不是 GPUI 界面与 agent 的日志格式。
- 目录：Windows exe 同级 `logs/`；Linux `~/.local/share/fluxdown/logs/`。文件名 `fluxdown_YYYY-MM-DD.log`，单卷 2MB 分卷，总量超 `log_max_size_mb`（默认 10MB）从最旧删，保留 7 天。
- Rust：`use crate::logger::log_info; log_info!("[mod] ...")`（Rust 2024 无 `#[macro_use]`，每文件显式 use）。
- GPUI 任务「日志」另走引擎数据库中的结构化活动历史（`engine/task_activity.rs`、`db.rs`），不是全局滚动文本文件：源端时间、跨重启 ID、查询分页与实时通知配合。当前保留七天且全库最多五万条，两者先到先清理；页面显示保留截断。同步事件入有界队列，持久化失败不广播成功记录，队列溢出/失败形成显式 `journal_overflow` 缺口；关机冲刷有界，不能因日志数据库不可用永久挂住。

**GPUI 桌面链路（desktop / agent / daemon）**——desktop / agent 文本日志独立，daemon 沿用引擎滚动日志：
- `fluxdownd`：沿用引擎 `logger`（`<engine 数据目录>/logs/fluxdown_*.log`）；`main` 返回错误时带完整错误链落盘。目录总大小上限是 **daemon 配置键** `log_max_size_mb`，唯一类型/范围/默认值目录在 `native/protocol/src/daemon_config.rs`（整数 1–1024 MB，默认 10）；`native/daemon/src/actor.rs::{apply_log_limit,log_limit_bytes}` 在启动加载及该键提交后应用，缺失/非法持久值回退默认。它不控制 desktop / agent 的固定 2MB 单文件轮转。
- `fluxdown-desktop` 与 `fluxdown-agent`（非 `--server`）：共用 `native/logfile`（`fluxdown_logfile`，零依赖），写 `<agent 数据目录>/logs/{desktop,agent}.log`。单文件 2MB 轮转为 `.log.1`（只留一份，每进程 ≤4MB）；每个文件开头有会话头（版本、exe、参数形态、平台、`SESSIONNAME`/显示协议、`GPUI_*`/`ZED_*` 原值、其余 `FLUXDOWN_*` 只记名字），轮转后重写；同一消息（数字归一）每 60s 只落 10 条，其余汇总成 `[suppressed N repeats over Ts]`；UTC 时间戳；panic 带回溯。
- desktop 收 `log` 门面：`fluxdown*` 与 `gpui*`（含显卡选择、D3D 特性级别、DirectComposition、设备丢失、draw 失败）按 `FLUXDOWN_LOG_LEVEL`（缺省 info），第三方只收 warn+；另记窗口打开参数、首个窗口 GPU 规格（软件渲染告警）、首帧耗时 / 10s 无首帧告警、UI 线程心跳看门狗（停摆 10/60/300s 告警，macOS 因 App Nap 不启用）、agent 连接状态迁移与 agent 进程拉起/退出。启动参数只记开关与位置参数个数，不记链接。
- agent 收 `tracing`：`RUST_LOG` 非空时原样生效，否则 `warn` + 第一方 crate（含 `fluxdown_daemon`）按 `FLUXDOWN_LOG_LEVEL`；daemon 子进程 stderr 追加到同目录 `fluxdownd.stderr.log`（超 1MB 截断），拉起 / 非零退出（含存活时长）记入 `agent.log`。`--server` 模式仍是 stderr tracing。
- 移动端本机主机（`native/mobile/src/local.rs`）在启动进程内 daemon **之前**调 `fluxdown_agent::logging::init_embedded`：daemon 只在无全局订阅者时才装 stderr 订阅者，顺序反了 agent / daemon 的 tracing 全部丢失（手机没有可读 stderr）。进程级只初始化一次。
- Doctor 的日志目录检查、「打开日志目录」、日志导出都指向 `<agent 数据目录>/logs`（`log_export::agent_log_dir`）。嵌入宿主（`start_embedded`）的 Doctor 不产出 `app_listener` / `local_server` / `disk_sleep`（`DiagnosticsService::for_embedded_host`：无 TCP 网关 / NMH IPC / 兼容 API，也无机械盘），网关虽是 server 模式但放行 `agent.diagnostics.exportLogs`（`GatewayService::with_local_log_export`：只有同进程 App 能连，目标是 App 沙盒路径）。

**导出脱敏的唯一规则源**：`native/logfile/src/sanitize.rs::SANITIZE_PATTERNS`，由 `fluxdown_logfile::SANITIZE_PATTERNS` 导出；引擎 `logger::{sanitize_log_str,sanitize_log_bytes}` 与 agent `log_export::sanitize_text` 各自编译同一规则并按表顺序套用，不再维护两份正则。覆盖 URL userinfo、Telegram bot 路径令牌、敏感 query、超长 query、Cookie / Authorization、代理凭据与 Linux / Windows 用户目录；非 UTF-8 按有损解码后脱敏。规则用于导出，不代表原始落盘日志已脱敏；agent 的配置快照导出另先按结构清掉秘密字段（`sanitize_json_export`）。

## 发布与 CI（`.github/workflows/release.yml`）

**主干 CI**（`.github/workflows/ci.yml`）：`main` push 与所有 pull request 触发（`workflow_dispatch` = 忽略路径过滤的全量运行，发版前在发布分支上跑），`paths-filter` 分别判定 Rust / Web SPA / 官网 v2 / 扩展 / 插件 SDK，取消同分支或同 PR 的旧运行。Rust 门禁为 `cargo fmt --check` 与 `cargo clippy --workspace --all-targets -- -D warnings`（含测试等全部 targets），外加插件桌面类型漂移检查 `cargo run -p fluxdown_ui_plugin_ui --example gen_plugin_typings -- --check packages/plugin-sdk/types/desktop.d.ts`；`clippy.toml` 只放行测试中的 unwrap / expect，其余 lint 与生产一致。nextest 按 engine / engine-plugins（`--features plugins,components`，quickjs-jit 运行时与常驻宿主）/ core / agent / mobile / GPUI 分组、显式 `-p`，不跑 workspace 测试。Web SPA 做 lint + test + build（跨实现夹具 `plugin_view_apply.json` / `plugin_view_tones.json` / `consent_cases.json` 变化也触发），官网 v2 当前做 test，扩展分别构建 Chrome 与 Firefox；插件 SDK（`packages/plugin-sdk`，独立 bun 工程）做 `gen:check`（view / theme 类型与 `plugin_view_schema.json`、主题 `registry.json` 不漂移）+ typecheck + test（复用 `native/engine/src/plugin/fixtures/manifest_cases.json`）+ build。**发布对齐**（把只有发布才走的路径提前到合入时）：rust-lint 另跑 `.github/scripts/verify_librqbit.py`（librqbit 来源，与 release 共用）与 release `build-linux` 原样的 `cargo check -p fluxdown_ui_app -p fluxdown_agent -p fluxdown_daemon -p fluxdown_nmh --features fluxdown_agent/desktop --bins`（依赖特性合并只在这条组合出现）；`docker-context` job 构建 `docker/server.Dockerfile` 的 `server-check` 阶段（与 `server` 共用 `server-src` 的 COPY 清单，Web 前端 + `cargo check`，单架构），`.dockerignore` / COPY 漏东西在合入时暴露。它不发布资产；release 的 `verify-engine` 只剩 CI 不覆盖的 librqbit MSE fork 单测。

**插件 SDK 发布**（`.github/workflows/plugin-sdk-release.yml`）：推送 `plugin-sdk-vX.Y.Z` tag 触发，与应用 `v*` tag 互不影响；校验 tag 版本 = `packages/plugin-sdk/package.json` 的 version，跑 gen:check / typecheck / test / build 后 `npm publish --access public --provenance`。前置：npm 组织 `fluxdown` 与仓库 secret `NPM_TOKEN`（缺失则只在 publish 步失败）。`release.yml` 的 `changes` 把 `packages/*` 映射为不触发任何组件。发布成功后用 secret `PLUGIN_INDEX_TOKEN`（对 `zerx-lab/fluxdown-plugin-index` 有 Actions 写权限）`gh workflow run sync-validator.yml -f version=X.Y.Z`，索引仓把 npm 包里的 `dist/manifest.mjs`（首行 `// fluxdown-plugin-sdk@X.Y.Z …` 版本标记）同步为 `vendor/fluxdown-plugin-manifest.mjs`；secret 缺失时索引仓每日定时同步兜底。插件准入规则因此**只经发版 SDK 生效**，不再手动拷贝。

**组件变更检测 + 统一 release** 流水线，`v*` tag 触发。`changes` job diff `PREV..TAG` 映射路径→输出（`app`/`extension`/`server`/`mobile`/`ios`/`cli`），首个 tag 全量构建；**基线 `PREV`**：稳定 `vX.Y.Z` 取上一个稳定版（`git describe --exclude 'v*-*'`，跳过其间全部 `-rc.N`，rc 阶段改过的组件都进稳定版），预览取上一个任意 `v*` tag；同一基线经 `changes.outputs.prev` 传给 release notes（稳定版 git-cliff 以 `GIT_CLIFF__GIT__IGNORE_TAGS` 忽略 rc tag，说明覆盖整个 rc 周期）。同时解析构建源码 `source`（默认 = tag 提交）。**分支守卫**：稳定 `vX.Y.Z` 必须是 `origin/stable` 祖先；预览 `vX.Y.Z-rc.N` 必须在 `origin/main`；否则整条失败。同一 tag 的运行由 `concurrency` 串行。

**浏览器扩展**与其他组件同一套变更判定：预览 tag 有变动只打包附到 release（Chrome zip + `FluxDown-<版本>-firefox-unsigned.zip`，manifest `version` 由 WXT 去掉预发布后缀、Chrome 带 `version_name`），**不推 Chrome/Edge 商店、不走 AMO 签名**（unlisted 签名也占 AMO 版本号，会与稳定版 `X.Y.Z.1` 冲突）；稳定 tag 有变动才打包 + 推三家商店 + AMO 签名 XPI。官网 `/api/release` 的扩展恒取稳定版。

**商店签名 CRX**（`.github/workflows/cws-crx.yml` + `.github/scripts/cws_crx.py`，每 2 小时 + 手动）：商店审核异步，推 tag 时拿不到新包，只能事后轮询商店 gupdate 接口；商店版本对应的稳定 release 缺 `-chrome.crx` 时下载商店 CRX，校验商店给的 sha256 / 大小、CRX3 头、扩展 ID（声明值与 RSA 证明公钥一致）、包内 manifest 版本，原样以 `FluxDown-<版本>-chrome.crx` 传 GitHub Release + OSS（Chrome 若拒收网页直接下载的 `.crx`，官网 / 文档提示「链接另存为」）。最新稳定扩展 release 超 7 天仍高于商店版本时打 warning（商店上传 / 审核失败在 release.yml 里 `continue-on-error`，这是唯一持续提醒）。项目没有扩展私钥（manifest `key` 是商店公钥），**不能自行打 CRX**；GitHub 的 `-chrome.zip` 是开发者模式解压包，浏览器永不更新。官网下载页两类严格分开：商店签名安装包（CRX + Mozilla 签名 XPI）与开发者模式解压包，`/api/release` 的 `assets.chrome_crx` / `extension_crx_version` 取最近带 CRX 的稳定 release（可落后于 `extension_version`）。

**一个 tag 一个 release**：`prepare-release` 生成双语说明并建草稿 `vX.Y.Z`（预览标 prerelease；说明经 `release_publish.py --seed-notes` 先写入本次应发布组件）→ 各 `build-*` 并行 → `upload-<组件>` 经 `.github/actions/release-upload` 上传产物（`--clobber`），**最后**上传完成哨兵 `SHA256SUMS-<组件>.txt`（补发时先删旧哨兵、清掉旧清单里不再产出的资产）→ `publish-release`（`.github/scripts/release_publish.py`，`always()`）合并哨兵为 `SHA256SUMS.txt`、刷新说明头部（`<!-- fluxdown:release:begin components=… expected=… docker=ok|pending … end -->`：已发布组件清单 + 服务器 / CLI / Android / iOS 安装说明，位于双语标记之前；`expected` = tag 推送与历次补发应发布组件的并集，`docker` = Server 镜像是否推送成功）。**只有 `expected` 全部有哨兵且 docker 非 pending 才草稿转正**（才产生 release `published` webhook、官网/客户端可见、Telegram 公告）；否则保持草稿，补齐的那次补发 / Re-run 转正，已发布的 release 不退回草稿；**latest 仅给「稳定版 + 桌面端完整 + 最高稳定版本」**。组件构建互不阻断：某组件失败只跳过它的 upload，其余照常上传，publish 以失败结束并在 job summary 列出补发命令；Server Docker 直推 ghcr、不阻断二进制上传。官网 `/api/release` 只认非草稿 release 中有哨兵的组件（`website-v2/src/lib/release-assets.ts`；唯 `ios` 在缺哨兵时按 IPA 资产名识别，兼容并入 release.yml 前直接挂载的 IPA），缺失组件回落到它上一个完整版本；`/api/changelog` 剥掉说明头部。历史拆分时代的 `server-v*`/`cli-v*`/`mobile-v*`/`extension-v*` release 仍被官网兼容识别，不再新建。

**发版公告**（草稿转正那次，`rehearsal=false` 且 `was_draft=true`；`continue-on-error`，失败不影响发布）：`notify-telegram` 用 `TELEGRAM_BOT_TOKEN`/`TELEGRAM_CHAT_ID` 直调 Bot API 发频道（Markdown → Telegram HTML，内联脚本）；`notify-qq` 跑 `.github/scripts/release_notify_qq.py`，把 POST `{"text"}` 发到 `secrets.QQ_RELEASE_WEBHOOK_URL`，即 TgBot（`tg-bot.zerx.dev`）bot 3 的 webhook 流程 18「FluxDown 发版公告」，转发到 QQ「FD会员专属群」（群号 1131397845，`tgChatId=-1131397845`）。QQ 只发 `<!-- fluxdown:lang:zh -->` 区块，缺这个区块就只发标题加链接；Markdown 转纯文本（`###` → 【】、列表 → •、链接 → 「文字 (网址)」），整行截断上限 2500 字。本地预览：`gh release view <tag> --json isDraft,isPrerelease,name,url,body > r.json && TAG=<tag> python3 .github/scripts/release_notify_qq.py r.json --dry-run`。轮换 webhook：TgBot `flow webhook 18 --rotate`，然后更新这个 secret。请求必须带自定义 User-Agent，否则 Cloudflare 以 1010 拒绝。

**补救**：偶发失败（源码无需改）→ 运行页 “Re-run failed jobs”（只重跑失败组件 + upload/publish；release 转正前 artifact 一直保留，超过 14 天过期后改用补发）。需改代码/打包 → 修复合入发布分支后 `gh workflow run release.yml --ref main -f tag=<已有 v* tag> -f component=<app|extension|server|cli|mobile|ios|changed> [-f source_ref=<分支|提交>]`：`source_ref` 须包含该 tag 且在发布分支上，缺省 = tag 本身；版本号、预发布标记恒取 tag；`changed` 按该 tag 的变更检测补发全部应发组件；源码 ≠ tag 时补跑 librqbit MSE 门禁。源码取 tag 本身时 Server Docker 仅从 workflow 提交覆盖 `.dockerignore` 与 `docker/server.Dockerfile`（修打包不动源码）。拆分时代的旧 release（无哨兵）拒绝补发。预览镜像不更新 `latest`。

**演练（rehearsal）**：发版前验证整条流水线而不发布：`gh workflow run release.yml --ref <main|stable> -f rehearsal=true -f tag=<尚不存在的 v* tag> -f component=all`（`changed` = 按真实变更检测，单组件亦可）。tag 必须**尚不存在**、不接受 `source_ref`：构建源码即 `--ref` 所指提交（workflow 文件与源码同一提交，同 tag 推送）；`changes` 在 runner 内打本地 tag（不推送），分支守卫、基线、变更检测、`is_highest_stable` 与真实发布同一套逻辑。照跑：librqbit MSE 门禁、全部构建与打包、macOS 签名 + 公证、Android 正式签名、Linux deb 冒烟、Web/Server/NAS/CLI、Docker 双架构构建并**只按 digest 推送**（无 tag、不可见，digest 存 `docker-digest` artifact）、git-cliff + Claude 发布说明（job summary + `rehearsal-release-notes`）、`release_publish.py --rehearsal-dir`（`rehearsal-release-preview`：总 `SHA256SUMS.txt`、`release-body.md`、计划中的 gh 操作）、OSS `ls` 只读探活（`oss-upload` `dry-run`，失败即红）、稳定版另加 `web-ext lint` 与 AMO/Chrome/Edge 凭据只读探活（并检查 AMO 的 `X.Y.Z`/`X.Y.Z.1` 未被占用）。不做：建 release、上传资产、OSS 上传、Docker 打 tag、商店提交、AMO 签名（listed/unlisted 都会永久占用版本号；Firefox 改出未签名包）。防误触：`rehearsal` 只能手动勾选且默认关，tag 推送恒为非演练；勾了演练却填已有 tag、未勾却填未来 tag、补发选 `all` 都在 `changes` 报错；副作用步骤一律以 `rehearsal == 'false'` 放行（输出异常按演练处理），演练与真实发布分属不同 `concurrency` 组，运行名带「演练」字样。

**只构建一次（演练产物晋升）**：稳定版发版顺序 = 全量 CI（`gh workflow run ci.yml --ref stable`）与演练（`-f component=changed`，tag = 即将发布的版本）在 stable 目标提交上并行跑 → 都绿后推 tag。tag 推送的 `changes` 先过 **CI 门禁**（`.github/scripts/release_gate.py ci-gate`：该提交最近一次 `ci.yml` 必须 success，仍在跑则等待，红即在建草稿前失败），再 `find-rehearsal` 找同提交、run-name「Release 演练 <tag>（不发布）」的运行：已有 `rehearsal-sums-<组件>` 哨兵（server 另需 `docker-digest`）的 app / server / cli / mobile / ios 跳过构建，`upload-*` 以 `run-id` 取演练 artifact，Docker 用 `docker buildx imagetools create` 给演练 digest 打版本 / latest tag；扩展恒重建（商店提交在同 job）。找不到可复用演练则照常全量构建。演练里组件失败 → 演练运行页 Re-run（未发布任何东西）；预览版可直接推 tag（全量构建）。构建 job 不再等 `verify-engine`（不占关键路径），upload-* 与 Docker 推送要求它成功。

**Artifact 与缓存容量**：artifact 只是中间产物，Release 资产独立存储（单文件上限 2 GiB，不计入 Actions 存储）。`cleanup-artifacts`（`.github/scripts/release_artifacts.py`，tag 推送 / 补发 / 演练都跑）按运行名里的 `v*` tag 判定：tag 的 release 已正式发布 → 删除该版本全部运行（tag 推送、演练、补发、iOS）的 artifact；草稿或未建 → 保留（晋升与 Re-run 要用）；进行中运行不动。所有 release.yml（含被复用的 `ios-sideload.yml`）artifact 带 `retention-days: 14` 兜底，被放弃的演练自动过期。一个完整版本的产物约 1.6 GB，最多在 Actions 停留到该版本转正。**配额**：仓库公开，标准 GitHub 托管 runner 的分钟数与 artifact 存储不计入账户套餐（Pro 的 1 GB「artifact + Packages」共享额度只约束私有仓库与私有包；ghcr 镜像公开）；若改为私有仓库，演练产物会消耗这份额度，超额且无付款方式时 `upload-artifact` 失败 → 对应组件没有哨兵、release 停在草稿，不会发布半套，释放额度后 Re-run。**缓存**：每仓库 10 GB，超出按 LRU 淘汰、不会让 job 失败。缓存按 ref 隔离，tag 作用域的缓存之后任何运行都恢复不了（v0.6.3 的 iOS 构建在 v0.6.2 已存同 key 缓存时仍 `No cache found`），所以 release.yml / `ios-sideload.yml` / `ios-testflight.yml` 在 tag 推送运行只恢复不保存（Swatinem `save-if`、`actions/cache/restore` + 条件 `actions/cache/save`）；`cleanup-artifacts` 同时删除已发布 tag 作用域的缓存（API 返回的 ref 可能是 `refs/heads/refs/tags/<tag>`）。新增 tag 触发的 workflow 也要照此处理缓存。

**自动重跑**（`.github/workflows/release-auto-rerun.yml` + `.github/scripts/release_auto_rerun.py`）：Release / iOS TestFlight 首轮失败时，除 Publish Release（组件不齐时按设计失败）外每个失败 job 的日志都命中瞬时模式（NSURLErrorDomain -1001/-1005/-1009、codesign 时间戳、ASC -19241、HTTP 5xx 等）才 `gh run rerun --failed` 一次；确定性错误不重跑。TestFlight 上传（`testflight.sh`）另对同类错误退避重试。

路径→组件映射以 `.github/workflows/release.yml` 的 `changes` job 为准：`fluxDown/*`→extension；`web|docker/*`→server；`crates/*`→app；`mobile/Android/*`→mobile；`mobile/FluxDown/*` 与 `.github/workflows/ios-sideload.yml`→ios；`native/mobile` 与共享 Rust 核心、protocol、agent/daemon、assets/i18n 的改动同时触发 mobile 与 ios，并覆盖其 PC / headless 消费者。旧 Flutter 目录与旧 headless 宿主 `native/server` 均已移除。

- **存储与本地执行边界**：agent 只在会话目录 `/tmp/fd-work/<随机>` 里工作（blobless 克隆，结束 `rm -rf`），不在服务器构建 / 测试 / 安装依赖，构建与测试一律交给 CI；工具链里的 `cargo` 经 `toolchains/guard/cargo` 包装，只放行 `update` / `metadata` / openapi 生成器，且 `CARGO_TARGET_DIR` 必须在会话目录内。`janitor.py` 由 gate 每小时触发：回收 12 小时未动的会话目录（修复分支结束或 7 天未动的 `fix-*`）、3 天前的自动化运行目录、cargo 解压源码与超 1.5GB 的下载缓存、30 天未更新的 OpenHands 会话，每周 `omp gc --apply`；空闲低于 15GB 每天发信，低于 6GB 先就地回收、仍不足则拒绝派发新会话。
- **omp 每日自动更新**：宿主机 systemd 定时器 `fd-omp-update.timer`（每天 05:10 UTC+8，落在不合并时段）执行 `bin/omp-auto-update.sh`：`omp update --check` → 备份 → `omp update` → 核对宿主机与容器版本 → 容器内 sonnet / opus 各一次真实请求冒烟 → 失败回滚到备份 → 只保留当前版本的 natives（每版约 365MB，宿主机与容器各一份）；只有升级或失败才发信，日志 `data/fd-omp-update.log`。容器经目录挂载 `/root/.local/bin → /opt/omp-host` + `bin/omp-shim` 使用宿主机同一份二进制（`omp update` 以替换文件方式升级，单文件挂载会一直指向旧 inode），新会话立即用新版本，无需重启容器。
- **跨系统同步点**：改 `.github/workflows/ci.yml` 的 paths-filter 分组或 job 名，要同步服务器 `classify.py` 的 `CI_GROUPS` / `CI_JOBS`（否则合并门会误判 CI 覆盖）；新增 GPUI crate / 页面目录时同步 `classify.py` 的 UI / 纯逻辑路径表。

  - **rqbit fork**（`zerx-lab/rqbit` 分支 `fluxdown/main`）：钩子集中在 `crates/librqbit/src/peer_policy.rs`（`PeerPolicy::{admit, readmit, on_event}` / `PeerCtx` / `PeerEvent` / `PeerVerdict`，经 `SessionOptions.peer_policy` 注入，`None` 时只保留两项通用修复）。判定在单连接内只升不降：Throttle = 会话级共享受限桶（`Session::set_throttled_upload_bps`，每连接最多 4 个排队请求；不占上传槽，对端感兴趣即 unchoke）、Choke = 永不再给上传槽（Choke 报文由 choker 发、恰一次，已排队上传丢弃）、Disconnect = 断开；`Session::{disconnect_peers_where, readmit_refused_peers}`。判定经 `PeerPolicyBinding::dispatch` 的返回值交 choker 执行（`choker.rs::SlotClass`，见 engine.md「BT 上传对端选择」）。`Disconnected` 每个已握手连接恰报一次（暂停 / 删除 / 关会话由 `PeerPolicyBinding::drop` 兜底）。magnet 取元数据拨号同样经 `admit`；重试路径用 `readmit`，不计入拒绝统计。**通用修复**：始终发冗余 HAVE（原先对已有该片的对端不发，会被 PBH `ProgressCheatBlocker` 误判为假进度）；发送前丢弃对端已 Cancel 的块；普通上传队列每连接排队上限。
